PlanBench: the standard test of planning in language models

PlanBench is a public benchmark that asks a language model to plan, and checks every answer with a real plan validator. It is the benchmark PDDL-INSTRUCT reports on, and the source of the Blocksworld and Mystery domains used on this site.

1

What it is

A benchmark built from classic planning-competition domains, graded automatically.

PlanBench was created by Karthik Valmeekam, Matthew Marquez, Alberto Olmo, Sarath Sreedharan and Subbarao Kambhampati (Arizona State University). It was published in the NeurIPS 2023 Datasets and Benchmarks track (arXiv 2206.10498), and its code and data are open on GitHub.

Its point is simple: many papers claimed language models could plan, but tested them on everyday tasks where a plausible-sounding answer is hard to grade. PlanBench uses domains from the International Planning Competition, written in PDDL, so every plan can be checked exactly by a validator. Nothing is graded by eye.

In one box

  • Domains: Blocksworld, Logistics, their "Mystery" versions; Depots added later
  • Instances: 600 Blocksworld, 285 Logistics
  • Prompts: about 26,250 across all test cases and domains
  • Test cases: 8, from plan generation to replanning
  • Grading: the VAL plan validator; optimal plans from the Fast Downward planner
  • Licence: MIT (code repository)

Eight test cases

Not only "make a plan": also check, predict, reuse and repair plans.

#Test caseThe question it asksBlocksworld prompts
1Plan generationWrite a valid plan that reaches the goal.600
2Cost-optimal planningWrite the shortest (cheapest) valid plan.600
3Plan verificationWill this plan work? If not, which action fails and why?600
4Reasoning about plan executionWhat is the state after these actions?600
5Robustness to goal reformulationRecognise the same goal written differently (reordered, or stated fully vs partly).600 each
6Plan reuseUse part of a plan you have already seen.600
7ReplanningSomething unexpected changed the state; make a new plan.600
8Plan generalizationSpot the pattern in example plans and apply it to a new problem.500

Link to PDDL-INSTRUCT: its Phase 1 practises plan verification (test case 3: explain why each action is valid or not) and execution reasoning (test case 4: track the state), and is evaluated on plan generation (test case 1).

A problem file

Each instance is an ordinary PDDL problem: objects (blocks named by letters), the initial facts and the goal facts. For example, the first generalization instance starts with eight blocks all on the table and asks for one tall tower.

A prompt (plan generation, one-shot)

The model never sees PDDL in the standard setting. The domain is described in plain English, blocks get colour names, and one solved example comes before the real question. Shortened, with the structure kept:

1. Domain in words
I am playing with a set of blocks ... Here are the actions I can do:
  Pick up a block · Unstack a block from on top of another block
  Put down a block · Stack a block on top of another block
I have the following restrictions on my actions:
  I can only pick up or unstack one block at a time. ...   (11 rules)

2. One solved example
[STATEMENT]
As initial conditions I have that, ... My goal is to have that ...
My plan is as follows:
[PLAN]
unstack the blue block from on top of the orange block
...
[PLAN END]

3. The real question
[STATEMENT]
As initial conditions I have that, ... My goal is to have that ...
My plan is as follows:
[PLAN]                                  ← the model continues from here

The stored answer and how it is graded

ground_truth_plan
(unstack yellow orange)
(put-down yellow)
(pick-up orange)
(stack orange red)
  1. The model writes one action per line in English.
  2. A template-based translator turns each line into a PDDL action.
  3. The VAL validator runs the plan from the initial state and checks every precondition and the goal.
  4. For cost-optimal planning, the plan length is also compared with the optimal plan from Fast Downward.

Mystery: hiding the meaning

If a model really reasons, renaming the words shouldn't matter. It matters a lot.

Mystery Blocksworld keeps the rules exactly but renames everything. In the deceptive version the new words are real words with misleading meanings; in the randomized version they are random strings. The deceptive Blocksworld domain in the repository (named mystery-4ops) uses:

Blocksworldpick-upput-downstackunstackontableonclearhandemptyholding
Mysteryattacksuccumbovercomefeastplanetcravesprovinceharmonypain

This is the same renaming used on this site. Logistics has its own deceptive words.

How models score

Large models manage some Blocksworld problems; almost none solve Mystery, unless they are reasoning models.

Plan generation, zero-shot (repository leaderboard, 600 problems each)

Ordinary language models score 0–1% on Mystery even when they reach 35–63% on Blocksworld: they lean on what the words usually mean. Reasoning models that "think" at length before answering do much better, but still lose a lot when the words are hidden. Leaderboard numbers are zero-shot, so they differ slightly from the paper's one-shot table.
