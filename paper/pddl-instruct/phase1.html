Phase 1

Instruction tuning: learning the language of checking

The base model solved none of the 200 test problems. Phase 1 shows it 1,440 worked examples, every one written by the exact checker, so it learns to reason about plans the way the checker does: preconditions, effects, new state, goal.

1

The training data

480 problems, three examples each: 1,440 examples, all correct by construction.

A generator makes Blocksworld problems from a seed: a random start arrangement and a random goal. The same problem is also written in Mystery names. For each problem the A* planner finds the shortest plan, and the checker writes the explanations.

Each set uses its own range of seeds (0, 100,000 and 200,000 apart), so no test problem can appear in training.

2

Three kinds of example

Two teach checking a plan. One teaches writing a plan in a checkable form.

Explain a correct plan

480 Given the domain, the problem and the shortest plan, walk through every action and show why it works.

Find the error in a broken plan

480 The correct plan is broken on purpose. Walk through it and name the exact fact that fails.

Plan step by step

480 Only the domain and problem are given. Write the plan, checking each step, and end with a final plan line.

How plans are broken

The generator picks one of four changes at random and keeps trying (up to 50 times) until the checker rejects the result. It succeeded for all 480 problems.

What the model is graded on

    
Only the answer. The prompt is hidden from the loss.

    
Each example is wrapped in the model's chat format (user turn: the prompt; assistant turn: the target) and turned into tokens. The prompt's labels are set to −100, which the loss ignores, so the model is never asked to memorise the domain text, which is the same in every example. An end-of-text token is added so it also learns where to stop.


tokens: [ prompt tokens ................ ][ answer tokens ......... END ]
labels: [ -100 -100 -100 ... -100        ][ answer tokens ......... END ]
                ignored by the loss              graded, token by token

    
The loss is cross-entropy: at each answer position, how much probability the model gave to the checker's next token. Examples average 1,261 tokens; the longest are cut at 3,072.

    
Why instruction tuning and not plain fine-tuning? One model must do three jobs (explain, find errors, plan), and later a fourth (repair from feedback). The instruction at the top of each prompt says which job it is. And the target is written reasoning, not just a label or a plan, so the model can't take shortcuts, and in Phase 2 the checker can grade every step it writes.

LoRA: training 1.2% of the model

    
Full fine-tuning needs over 20 GB of GPU memory. LoRA fits in 8 GB.

    
LoRA freezes all of the model's original weights and adds two small matrices beside each chosen layer. Only those are trained. The paper used full fine-tuning; this rebuild uses LoRA because of the laptop GPU.


output = W_frozen · x  +  B · A · x        A: 16 × d,  B: d × 16  (rank 16)

5

    
The training run

    
One pass over the 1,440 examples: 90 updates in 82 minutes.

    

      
Training loss

    

    
The loss falls very fast because the format is rigid: once the rules are learned, the next token is almost always predictable. A loss of 0.005 means the model can reproduce the training answers nearly perfectly. It doesn't mean it can solve new problems; only the test can show that. The run saves a checkpoint every 20 updates and resumes automatically, so a laptop shutdown loses only minutes.
