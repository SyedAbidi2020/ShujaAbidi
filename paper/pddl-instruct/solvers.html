Classical planning

Exact solvers: perfect inside PDDL, stuck outside it

Classical planners like A* and Fast Downward solve any problem written in PDDL, exactly and fast. So why train a language model to plan at all? Because real tasks rarely arrive as clean PDDL. This page explains what exact solvers do, where they stop working, and why a neural-symbolic approach such as PDDL-INSTRUCT is needed.

1

The exact solvers

Decades of research, used as the ground truth in every planning benchmark.

PlannerKindWhat it is known for
A*optimal searchThe textbook method: search states, guided by an estimate of the distance to the goal. Used in this project to make the training plans.
Fast Downwardplanning frameworkThe standard research planner, with many search methods and heuristics. PlanBench uses it for optimal plans.
LAMAfast, not always shortestA Fast Downward configuration built on landmarks (facts that must become true on the way). It won planning-competition tracks.
FF (Fast-Forward)fast, not always shortestEstimates distance by solving a relaxed problem that ignores delete effects.
PyperplanteachingSmall and pure Python; easy to install and read.
VALvalidatorDoesn't plan; checks plans. The model for this project's checker.

Their promise: give them a complete domain, an initial state and a goal in PDDL, and they return a plan that is guaranteed valid (and, with an optimal planner, guaranteed shortest), or prove that none exists.

2

How A* solves a problem

Try actions, keep the most promising states first, stop at the goal.

Problem bw-3-3005: c is on b, a is on the table, goal (on a c). A* keeps a queue of states ordered by f = g + h: g is the number of steps so far, h the number of goal facts still false. Because every missing (on x y) needs at least one stack, h never overestimates, so the first plan A* finds is the shortest.

On problems that are already written in PDDL, the exact solver wins on every measure: correctness, plan length, speed, hardware, and immunity to meaningless names. If the job is "complete PDDL in, plan out", use a classical planner.

4

Where classical planning fails

Not on hard PDDL problems, but on everything that has to happen before there is any PDDL.

An exact solver needs three things handed to it, all exact: the rules, the initial state and the goal. In real use, especially for robots working with people, at least one is usually missing or wrong.

SituationExampleClassical planner
Goal given in words"Tidy the meeting room before 3 pm."Can't start: "tidy" is not a PDDL fact. Someone must decide that cups go to the kitchen and the laptop stays.
Rules incompleteThe domain forgot that the robot needs a free hand to open a door.Plans "carry cup, open door". Legal in the file, impossible in reality. It can't notice, because it only knows the file.
New objects or skillsA tray appears that carries four cups at once.No action for it in the domain, so it can never use it.
State from sensorsThe camera says "probably a cup, maybe a bowl".Needs exact true/false facts; uncertain or missing facts break the model.
A person asks why"Why are you moving the box first?"Gives only a list of actions, no explanation in words.
Very large problemsHundreds of objects and actions.The number of states explodes (with 6 blocks there are already 7,057). Modern planners go far, but search can still become slow.
Important: a classical planner does not fail on unseen PDDL problems. Give it any new problem in a known domain and it solves it. It fails on unseen situations that nobody has written as PDDL. That is the gap neural methods are meant to fill.

5

Why neural-symbolic

A neural network for what is fuzzy, symbolic rules for what must be exact.

Neural (language model)

  • understands everyday language
  • brings common sense when rules are missing
  • handles new objects and situations
  • explains its reasoning in words
  • but makes confident mistakes

Symbolic (planner, checker)

  • exact and guaranteed correct
  • fast on complete problems
  • never fooled by names
  • checks every step
  • but needs everything written in PDDL first

Each side covers the other's weakness. PDDL-INSTRUCT combines them in two ways: the symbolic checker teaches the neural model (it writes the training reasoning and grades the model's plans), and the model learns to reason like the checker, stating every precondition, effect and state so that its plans can be verified.

Other neural-symbolic designs

  • LLM + planner ("LLM+P"): the language model translates the task into PDDL; a classical planner solves it exactly.
  • LLM + checker ("LLM-Modulo"): the language model proposes a plan, a checker verifies it, and feedback goes back until it passes.
  • PDDL-INSTRUCT: the checker is also used during training, so the model itself learns to reason in a verifiable way.

6

The honest summary

TaskBest tool
Complete PDDL in, plan outClassical planner (A*, Fast Downward, LAMA)
Checking a planValidator (VAL, or this project's checker)
Turning a person's words into goalsLanguage model, then check
Planning with incomplete rules, explaining to peopleNeural-symbolic: a model that reasons verifiably, with a checker in the loop

Why this project uses Blocksworld at all: not to beat A*, but because A* and the checker know the exact answer to every problem. That makes it a clean testbed to measure whether a language model can learn logical, checkable planning. Whether that skill carries over to everyday robot tasks is the next research question.
