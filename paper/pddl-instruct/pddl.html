Background

PDDL: the language of plans

PDDL describes a world as a list of true facts, and each action as the facts it needs and the facts it changes. That is all a computer needs to check any plan exactly. This page explains it with the classic test world, Blocksworld.

1

Two files: domain and problem

The domain gives the rules. The problem gives the start and the goal.

Domain: the rules (same for every problem)

(define (domain blocksworld)
  (:predicates (clear ?x) (ontable ?x)
               (handempty) (holding ?x) (on ?x ?y))
  (:action pick-up
    :parameters (?x)
    :precondition (and (clear ?x) (ontable ?x) (handempty))
    :effect (and (not (ontable ?x)) (not (clear ?x))
                 (not (handempty)) (holding ?x)))
  ; put-down, stack and unstack follow the same pattern
)

Problem: one task

(define (problem bw-3-3005)
  (:domain blocksworld)
  (:objects a b c)
  (:init (handempty) (ontable b) (on c b)
         (clear c) (ontable a) (clear a))
  (:goal (and (on a c))))

Three blocks. At the start c sits on b, and a is on the table. The goal: put a on c.

2

Facts

A state is the list of facts that are true. Anything not listed is false.

FactMeaningHere
(ontable x)x sits directly on the tableb, a
(on x y)x sits directly on top of yc on b
(clear x)nothing is on top of xc, a (not b)
(handempty)the hand holds nothingtrue
(holding x)the hand holds x in the airnone

So this state is exactly six facts:
(handempty) (ontable b) (on c b) (clear c) (ontable a) (clear a)

3

Actions: what they need, what they change

An action can happen only if all its preconditions are true. Then it adds some facts and deletes others.

ActionNeeds (preconditions)AddsDeletes
(pick-up x)
lift x from the table		clear x, ontable x, handemptyholding xclear x, ontable x, handempty
(put-down x)
put x on the table		holding xontable x, clear x, handemptyholding x
(stack x y)
put x on y		holding x, clear yon x y, clear x, handemptyholding x, clear y
(unstack x y)
lift x off y		on x y, clear x, handemptyholding x, clear yon x y, clear x, handempty

Everything follows from this table. To check a plan, start from the initial facts and, for each action, test its preconditions, then add and delete. No guessing is ever needed. That is why a computer can check plans perfectly.

4

A plan, step by step

The shortest plan for bw-3-3005 has two steps: pick up a, stack it on c.

[Action 1: (pick-up a)]
- Preconditions: (clear a) (handempty) (ontable a)
- Current state: (clear a) (clear c) (handempty) (on c b) (ontable a) (ontable b)
- All preconditions are satisfied
- Effects: add (holding a); delete (clear a) (handempty) (ontable a)
- Resulting state: (clear c) (holding a) (on c b) (ontable b)
[Action 2: (stack a c)]
- Preconditions: (clear c) (holding a)
- Current state: (clear c) (holding a) (on c b) (ontable b)
- All preconditions are satisfied
- Effects: add (clear a) (handempty) (on a c); delete (clear c) (holding a)
- Resulting state: (clear a) (handempty) (on a c) (on c b) (ontable b)

The goal (on a c) is satisfied in the final state. The plan succeeds.

This exact form of text, written by the checker, is what the model learns to produce in Phase 1.

5

How a plan fails

There are only two ways: an action whose preconditions are false, or a goal that is never reached.

Precondition violation

Swap the two steps, so the robot tries (stack a c) first:

[Action 1: (stack a c)]
- Preconditions: (clear c) (holding a)
- Current state: (clear a) (clear c) (handempty) ...
- VIOLATION: the precondition (holding a)
  is not true in the current state

The hand is empty. Nothing after a failed step can be checked.

Goal not reached

Stop after (pick-up a): every step is legal, but the job isn't done.

All actions are applicable, but the goal
is not reached: (on a c) is not true
in the final state.

The checker names the exact missing fact.

Language models make the first kind far more often. After Phase 1, 160 of the 172 wrong first tries failed on a precondition: the model lost track of the state, for example trying to stack a block it wasn't holding.

6

Mystery Blocksworld: logic without familiar words

The same world with every name replaced, so a model can't lean on what the words usually mean.

BlocksworldMystery
pick-upattack
put-downsuccumb
stackovercome
unstackfeast
ontableplanet
oncraves
clearprovince
handemptyharmony
holdingpain

The renaming comes from PlanBench. (craves c b) simply means c is on b, and (attack a) means pick up a. The rules are identical; only the words change.

A model that truly reads the rules in the domain file does equally well on both. A model that relies on what "stack" or "on" usually mean collapses on Mystery. That's why every result here is reported for both.

(:init (harmony) (planet b) (craves c b)
       (province c) (planet a) (province a))
(:goal (and (craves a c)))
; plan: (attack a) (overcome a c)

7

How big is the world?

The number of facts grows slowly. The number of arrangements explodes.

With n blocks there are n facts each for ontable, clear and holding, n×(n−1) for on, and one handempty: (n+1)² possible facts in total. Only a few are true at once: one position fact per block, one clear per tower, and the hand.

Our training and test problems use 3 to 6 blocks. A 6-block explanation can run to about 3,000 tokens, which is why longer problems are much harder for a small model. You can explore these worlds yourself on the Try It page.
